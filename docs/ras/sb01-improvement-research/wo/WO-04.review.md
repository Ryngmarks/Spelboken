# WO-04 review – Movement domain + schema

**Verdict: PASS WITH FIXES** · Reviewer: Claude (Opus 5.5) · 2026-10-29 · diff `e7c4c93..20b89de` (worktree t3-5b5e1635)
Lenses: code, critical. Every requirement and acceptance criterion is met except one way that hostile input gets past reconcile (M1).

## Findings
**Major**
- **M1 – Prototype-key ids keep an invalid link and cause a scenario to disappear later.** `movement.ts:55` (also `:76`, `:61`) checks
  `frame.positions[id]` on a plain object. Suppose an imported file has an entity with id `constructor`/`toString` and no position, plus an arrow with
  `entityId: "constructor"`. The lookup finds `Object.prototype` members, so the link is kept and rewritten to `from: {}, to: {}`. Verified:
  `parseScenario` returns that, and parsing the saved JSON again returns **null**. `localStore.list` then filters the scenario out, so it vanishes
  after the next save and reload. Fix: use `Object.hasOwn(positions, id)` in `reconcileLinks`/`ballHolder`, or build positions with
  `Object.create(null)` in `validate.ts:56`. Add a hostile test for it.

**Minor**
- **m1 – Stale `dribble` drags the ball back.** `movement.ts:71` follows any dribble arrow without checking that the carrier still holds the ball.
  Scenario: pass k→P9, P9 dribbles in k+1, coach re-targets the pass to P10. The ball is beside P10 in k+1 and jumps to P9 in k+2 (verified).
  Fix: follow a dribble only if the carrier is `ballHolder(k)`, otherwise demote it to `run`.
- **m2 – BALL_FOLLOWS=false never moves the ball.** `movement.ts:103` keeps the ball at `from` even for a pass into space. With variant B (k = current−1),
  a ball drag can then never place the ball. The blueprint only turns off *following*, and a pass into space puts the ball at `to`. The path is inactive
  (owner #7 = true), but it is not the fallback §2.1 describes. Suggest: when false, ball at `to`, no `targetId`.
- **m3 – Derived ball position silently overrides manual moves.** `moveEntity(s, k+1, 'ball', …)` while a targeted pass or dribble exists in k is
  undone by reconcile (verified, ball snaps back). This is correct per §2.1, but WO-05/06 must unlink or re-target on such a drag, or the Flytta tool looks broken.
- **m4 – `insertFrameAfter(k)` in the middle of a linked move.** The arrows in k now point at the copy: player arrows become zero length, while the ball
  is still forced beside the receiver in the copy, and the copy→k+2 move has no arrow. Invariants hold (tested), but the step semantics are lost.
  Consider moving k's linked arrows to the inserted frame.
- **m5 – Removing a dribble resets a pass into space in the same frame.** `removeLinkedMove` (`movement.ts:131`) restores ball k+1 := ball k even
  though a pass arrow still exists. The pass becomes zero length and its destination is lost (verified). This is a rare combination.
